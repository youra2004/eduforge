# ADR-0010: Experiment instrumentation

- The four counterbalancing cells (order × which topic gets the method) are filled by "emptiest cell first, random among ties" under an advisory lock, so after any N the cells differ by at most one. Topics A and B are courses named by `EXPERIMENT_COURSE_A/B` (slugs); the newest published version is used, so no new version of either may be published during a running study. Only the two tables of `DATA_MODEL.md` §13 exist: module state is derived from `assessments`, `enrollments` and `event_log`, and `module`/`condition` ride in each event's `props`, so the schema did not change.
- The control condition is enforced in the services, not the UI: enrolling opens every node, node tests (`node_test_disabled`) and the tutor (`tutor_disabled`) are refused. Control has practice questions as self-check and ends by an explicit "I'm done"; the method ends by passing all nodes. Pre-, post- and delayed tests use the module's whole `assessment` pool (same set for both conditions and all three tests, only the order differs), give no feedback and never touch BKT. The survey follows the post-test; the delayed test opens `EXPERIMENT_DELAY_SECONDS` after it (scaled by `TIME_SCALE`) and is reminded in the app, not by email.
- Browser-only events (`content_opened`, `video_progress`, `session_heartbeat`) go through one whitelisted endpoint; heartbeats are throttled on the server. The export is CSV per table, only the pseudonym `code` identifies a person, tutor messages and free text are not exported, and a column check refuses to build a file with a personal column. Withdrawal from the study is not built (deferred).
